Run-to-Run Hardware Noise Decomposition

Measured across 192 replicate groups of identical jobs:

  • Runtime noise (σnoise): 0.119 log-sd (~12.6% run-to-run variation)
  • CPU-time noise: 0.110 log-sd
  • ML Inference overhead: 18.20 ms for entire batch
  • Model artifact size: 2612.2 KB

By subtracting run-to-run noise from total model residual variance, GreenThread avoids overfitting mode-choice gates to stochastic operating system jitter.

Why This Matters in Review II Demo:

Conventional schedulers and cloud carbon models assume Time-of-Use accounting (charging battery jobs at grid intensity when running). Because energy was stored hours earlier, ToU accounting creates up to +50.6% overcounting (when running on dirty grid with solar-charged battery) and -39.5% undercounting (when running on clean grid with coal-charged battery). GreenThread's continuous state ledger records exact charge-time intensity, solving this material gap. Zero-accounting (calling battery energy "free") is -100% incorrect everywhere.

9 Architectural Evolution: Version 1 → Version 1.1
● Measured on my laptop Engineering changes made after Review I
1. Uncertainty Discounting & Forecast Freshness
Version 1 Problem

Fixed exponential decay: Distrusted accurate forecasts just as much as inaccurate ones, and shrank toward a flat daily mean, destroying the diurnal day/night opportunity.

Result: Cost carbon without paying off.

Version 1.1 Solution

Adaptive Bayes-optimal weighting: Scores its own past forecasts per lead time and shrinks toward hour-of-day climatology.

Result: +1.3 to +3.1 pt gain under misleading forecasts without hurting oracle signals.

2. Deadline Feasibility Constraint
Version 1 Problem

Loose deadlines: Workloads had 5–10× slack; the deadline feasibility check was never exercised during testing.

Result: False confidence in simple scheduling.

Version 1.1 Solution

Tight-deadline workloads (1.25–3×): Added upper-quantile (q0.9) constraint + switchable escalation benchmark.

Result: Quantile keeps miss rate at 0.07% vs 0.14% on always-ECO.

3. Battery Execution Mode Selection
Version 1 Problem

Winner's Curse: Schedulers picked the cheapest of several noisy estimates, and simulation treated run-to-run noise as model error.

Result: Always-ECO beat GreenThread on battery.

Version 1.1 Solution

Empirical-Bayes shrinkage + pessimism margin: Decomposed noise (σnoise = 0.119) and shrunk predicted mode effects toward population priors.

Result: Matches ECO energy saving while protecting deadlines.

4. Hardware Measurement vs Assumption
Version 1 Problem

Assumed saving: Relied on literature claim that EcoQoS cuts power by 42%.

Result: Unverified assumption.

Version 1.1 Solution

Direct battery power telemetry: Implemented idle and calibrate commands.

Result: Discovered EcoQoS actually increases energy by 19.6% on AMD Ryzen (H7 overturned!).
